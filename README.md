# dataforge

> **All data in this repository is synthetic.** It's generated by
> `scripts/generate_mock_data.py` from a fixed seed and refers to no real person or
> organisation. IPs use the reserved TEST-NET-2 range and emails use the `.invalid` TLD.

---

## What this is

A reusable pipeline pattern for data products: **a framework plus a reference
implementation**, not a single pipeline.

There's no `orders_pipeline.py`. One contract-driven runtime handles four data products,
each defined by a YAML file. Adding a fifth means adding a YAML file and getting it
reviewed. No new Python, DAG or deployment.

```
contracts/orders.yml ──┬──► ingestion plan      (what to read, how to increment)
                       ├──► physical schema     (Arrow/Iceberg schema, generated)
                       ├──► quality rules       (what's acceptable, what to do if not)
                       ├──► privacy policy      (what's sensitive, how it's masked)
                       ├──► storage layout      (partitioning, clustering, retention)
                       ├──► the Airflow 3 DAG   (generated by a factory)
                       ├──► the CI gates        (validity + schema evolution)
                       └──► lineage + runbook   (emitted, never hand-maintained)
```

A bespoke pipeline per dataset is quicker to start, but by thirty datasets the
duplication is what slows the team down. See
[ADR-0002](docs/adr/ADR-0002-declarative-contracts.md).

**What's included:** a Python package with a full test suite, four contracts covering
files, CDC, streams and a REST API, an Airflow 3 DAG factory, a dbt project with custom
generic tests, a Docker Compose stack with an emulated-AWS overlay, and CI on GitHub
Actions.

## Quick start (Docker only)

**You only need Docker Desktop**, with at least 4 GB of memory. No Python, virtualenv or
dbt on your machine.

```bash
make build      # build the image everything runs on (3-6 min the first time)
make verify     # end to end: 4 source types -> lake -> dbt marts -> 50 tests
make up         # start Airflow 3 at http://localhost:8080 (no login, local only)
```

`make verify` should end with:

```
Done. PASS=50 WARN=2 ERROR=0 SKIP=0
  End to end OK: 4 source types ingested, marts built, dbt tests passed.
```

The two warnings are expected. They come from referential-integrity tests set to `warn`,
because a new customer can show up in orders before the CDC feed catches up. **Green with
two warnings is a pass.**

Step by step:

```bash
make seed              # synthetic source data, with injected defects
make pipeline          # ingest files + CDC + stream + REST API
make dbt-docker        # build the marts and run the dbt tests
make test-docker       # the Python test suite
make gate              # everything CI runs: lint, mypy --strict, contracts, tests
make shell             # interactive shell in the image
make down / make reset # stop / stop and delete all state
```

Optional, emulated AWS (S3 + Secrets Manager, no account needed):

```bash
docker compose -f docker-compose.floci.yml up -d floci
docker compose --profile tools run --rm tools "python scripts/floci_bootstrap.py"
docker compose --profile tools run --rm tools "python scripts/verify_cloud.py --bucket dataforge-lake"
```

Full runbook, including Apple Silicon notes and troubleshooting:
**[docs/12-docker-desktop-runbook.md](docs/12-docker-desktop-runbook.md)**. To run on
the host instead, see [docs/11](docs/11-local-setup-and-testing.md).

## Data flow

```
   SOURCES                 BRONZE              SILVER                GOLD
┌──────────────┐      ┌─────────────┐    ┌───────────────┐    ┌──────────────────┐
│ files (OMS)  │      │ as received │    │ typed         │    │ dim_customer SCD2│
│ CDC (Debezium)├─────►│ immutable   ├───►│ deduped       ├───►│ fct_orders       │
│ stream (Kafka)│     │ 14–90 days  │    │ masked        │    │ agg_revenue_daily│
│ REST (FX API)│      │ replay      │    │ partitioned   │    │                  │
└──────────────┘      └─────────────┘    └───────┬───────┘    └──────────────────┘
                                                 │
                             dataforge (Python)  │  dbt (SQL)
                                                 ▼
                                         ┌───────────────┐
                                         │  quarantine   │  full payload + rule ids,
                                         └───────────────┘  replayable
```

**Step order** (details in `src/dataforge/pipeline.py`):

| # | Step | Why it's here |
|---|---|---|
| 1 | read | Inputs depend only on `logical_date`, never `now()`, so runs are replayable |
| 2 | **bronze write** | **Before validation**, so a wrong rule can be fixed and replayed without asking the source to re-send |
| 3 | normalize | Values that can't be coerced go to quarantine instead of becoming NULL |
| 4 | dedupe / CDC collapse | Before validation, so normal redeliveries don't count as failures |
| 5 | validate | Before masking, since rules check real values (a regex can't check a token) |
| 6 | mask | Before silver, the first widely readable layer |
| 7 | publish | Merge into the partition and overwrite it in one commit |
| 8 | **watermark** | **Last, and only on success.** Moving it earlier can lose data |

Who reads what: **bronze** is for platform engineers (replay, forensics). **Silver** is
for analytics engineers, dbt, analysts and ML features. **Gold** is for BI, executives,
reverse-ETL and data science.

## Assumptions

These numbers shape the design. Change them and the design should change too.

| Dimension | Assumption | Impact |
|---|---|---|
| Volume | Orders ~5M rows/day (~2 GB); events ~200M/day (~60 GB); customers ~100k changes/day | Orders fit on one node; events need Spark/Trino at scale |
| Latency | Daily batch for orders/finance; hourly micro-batch for events | **Micro-batch, not streaming** (ADR-0007). Sub-minute latency would need a different architecture |
| Freshness SLO | Tier-1 24h, events 2h, CDC 6h | Drives the freshness rules and alerting |
| Reliability | 99.5% of runs within SLO; zero tolerance for silently wrong data | **Late can be fixed, wrong can't.** When in doubt, block instead of publishing |
| Team | 3–6 engineers, 20–50 data products within two years | Justifies a framework. For one product it would be overkill |
| Cloud | AWS-shaped (S3, Glue/REST catalog, Secrets Manager) | The storage interface avoids lock-in to one vendor |
| Sources | At-least-once delivery; CDC may replay; files may be re-sent corrected | Everything must be idempotent |

## Data quality

Each rule's severity is set **in the contract**, because the right choice depends on the
dataset.

| Severity | What happens | Use when |
|---|---|---|
| `blocking` | Nothing is published. Run exits 2; the manifest records why | The data can't be trusted: broken PK, future-dated watermark, volume collapse, any FX rate issue |
| `quarantine` | Bad rows are set aside with their full payload and every rule they broke; the rest is published | Occasional row-level defects |
| `warn` | Metric only | Worth tracking, not worth paging |

The same rule type can have different severities. `row_count_anomaly` is **blocking** on
`orders` (a half-empty extract is probably a truncated upload) and **warn** on
`customers` (CDC feeds have quiet days).

**Quarantine-rate limit.** If more than `max_quarantine_rate` of a batch is quarantined,
the whole batch is blocked. That catches cases like a schema change quarantining most
rows every night while nothing alerts.

**Quarantine can be replayed.** Rejected rows keep the full original payload plus every
rule id and reason, so once the source is fixed they can go back through the same
pipeline.

**Where checks run:** in CI (engine unit tests, the real pipeline over synthetic data
with known defects, and `dbt build`) and on every scheduled run. Results go to the run
manifest, the structured logs and the OpenLineage `dataQualityMetrics` facet.

## Orchestration (Airflow 3)

`airflow/dags/factory.py` generates one ingestion DAG per contract, plus a gold DAG
scheduled on Assets.

- **Assets.** Gold runs when its silver inputs are refreshed, not on a guessed cron time.
- **DAG bundles and versioning.** With a Git bundle, a re-run uses the code version it
  first ran with, so backfills are reproducible.
- **Task SDK.** Tasks have no direct metadata-DB access, so nothing here reads Variables
  or sessions at module level.
- **Freshness is checked on the data**, by a contract rule plus an external monitor, not
  by task duration. A DAG that never ran can't report that it didn't run.

`max_active_runs=1` per dataset is the key setting: two concurrent runs on the same
partition can lose rows.

Ingestion is **one Airflow task**, not four. The stages share one in-memory batch, and
splitting them would mean passing it through XCom or storage. Per-stage metrics are
already in the logs and manifest.

**Backfills:** trigger with `force_reprocess=true` for the dates you need. Writes are
partition-level merges, so repeating is safe, and the watermark never moves backwards.

## Security and privacy

- **Masking happens on write into silver**, not at query time. Query-time masking can be
  bypassed by querying the base table, copying data or restoring a backup. Raw values
  live only in bronze, which has short retention and tight access.
- **Keyed HMAC, not a plain hash.** Plain hashes of emails are easy to reverse with a
  dictionary. A secret key prevents that, and tokens stay deterministic so joins work.
- **Key rotation.** Every token carries its key version (`v1:…`), so old and new tokens
  can be told apart during a rotation.
- **No key, no run.** If masked fields are declared and no key is available, the pipeline
  fails instead of falling back.
- **Classification is enforced.** Tests check that every `pii`/`pci` field is masked,
  and the compatibility check treats relaxing a classification as breaking.
- **Secrets:** OIDC for cloud access (no static keys), secrets read at task start, and
  log redaction as a safety net. Contracts reference credentials by URI
  (`secret://platform/fx-api/readonly`), resolved through Secrets Manager or SSM.
- **Environments are separate databases**, not schema prefixes in one.

More in [docs/06-security-governance.md](docs/06-security-governance.md).

## Cost

Ordered by impact on the bill:

1. **Incremental over full refresh.** Rewriting years of history nightly to change a
   fraction of a percent is the biggest avoidable cost.
2. **Partition pruning**, then **clustering on two or three columns** at most.
3. **Right-sized files on write (256 MB target)**, instead of compacting later. Small
   files are the main hidden cost in object-store lakes.
4. **Retention by layer.** Events bronze is 14 days; orders silver is 7 years. A test
   checks bronze never outlives silver.
5. **Snapshot expiry.** Old Iceberg snapshots keep deleted files alive.
6. **Pre-aggregate only when it pays off** (lots of queries over lots of rows, stable
   grain). `agg_revenue_daily` has a reconciliation test against its fact table.

More in [docs/07-cost-and-performance.md](docs/07-cost-and-performance.md).

## Observability and lineage

Four metric families per run: **freshness, volume, error rate, completeness**. They're
emitted even when a run fails (`trigger_rule="all_done"`), because failed runs are the
ones you most need to see.

Lineage is **emitted by the pipeline** as OpenLineage events instead of being scraped
from SQL. Each event knows the run, the partition, the quality metrics and the contract
version. Field classifications are included, so a catalog can trace where PII flows.

To trace a number back to its source: gold row → `_run_id` → run manifest → source URIs
and input fingerprint → the exact bronze files.

## Trade-offs

| Decision | Chose | Over | Why, and when the other option wins |
|---|---|---|---|
| Framework vs bespoke | Contract-driven framework | One pipeline per dataset | Pays off from about 3 data products. For one, bespoke is better |
| Table format | Iceberg (prod) / Parquet (local) | Delta, plain Parquet, warehouse-native | Engine independence is cheap now and costly later. Delta wins in a Databricks-only shop |
| Python vs SQL | Python up to silver, dbt silver→gold | All dbt, all Spark | Paging, CDC, quarantine and secrets need Python; business logic belongs in dbt |
| Streaming | Micro-batch from a landed sink | Flink / Structured Streaming | An Airflow outage delays data but never loses it. Real streaming wins below a ~1 minute SLO |
| Quality default | Quarantine, blocking where needed | Fail fast everywhere | Failing on everything leads people to disable rules. FX rates are still zero-tolerance |
| Pipeline state | Warehouse `_control` tables | XCom / Variables | Runs outside Airflow, keeps a queryable history, survives cleared tasks |
| Ingest granularity | One Airflow task | Four tasks | Avoids pushing a large batch through XCom |
| Config | One explicit `PipelineConfig` | Env reads scattered in code | Config you can see in one place is config you can review |
| Test data | Synthetic, with injected defects | Clean fixtures / prod samples | Clean data tests nothing interesting; prod samples are a privacy risk |

## Known limitations

- The JSON state store is single-process. Fine locally, not for production; the
  `StateStore` interface makes it a swap, not a rewrite.
- The Iceberg engine is illustrative and has no tests. Plain Parquet on S3 has no atomic
  partition swap (see docs/11), which is exactly what Iceberg fixes.
- The REST source runs locally against a stub (`scripts/fx_api_stub.py`), not a real API.
- The emulated-AWS setup covers S3 and Secrets Manager only: no Iceberg REST catalog, KMS
  or IAM policy checks.
- Backfills are limited to `force_reprocess`: no window planner and no automatic
  cascade to downstream marts.
- Referential-integrity rules accept a set of known keys, but nothing loads one yet. RI
  is checked in dbt at the mart layer instead.
